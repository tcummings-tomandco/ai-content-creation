What is MCP and how does it change enterprise AI integration?

MCP (Model Context Protocol) is the open standard, donated by Anthropic to the Linux Foundation's new Agentic AI Foundation in 2026, that lets an AI system connect to any number of business tools and data sources through one shared interface instead of a custom integration for every pairing. For an enterprise wiring up 15 core systems, that turns 105 hand-built connections into 15.

What problem does MCP actually solve for enterprise integration?

Before MCP, every AI tool that needed live data from a CRM, a data warehouse or a ticketing system needed its own custom connector. Wire five AI tools to ten business systems by hand and that is fifty separate integrations to build, test and keep working as each side changes its API.

That is the classic M times N integration problem: M tools, N systems, M times N connections to maintain. (Anyone who has watched a Zapier account fill up with broken zaps already knows this pain without the maths.)

MCP turns that into M plus N. Each AI tool speaks MCP once. Each system exposes one MCP server. Any tool can then reach any system through the same interface, with no new connector needed every time a pairing gets added.

Picture a UK insurance broker running a policy admin system, a CRM, a claims platform and a document store. Wired up by hand, an AI assistant needs four custom connectors before a fifth tool even joins the stack, and every one of them needs its own fix whenever an upstream API changes. Under MCP, the broker builds four servers once and any AI tool the business adds afterwards reuses them without touching a line of the original integration code.

Tom & Co worked example: a business connecting 15 core systems (ERP, CRM, marketing automation, a data warehouse, a helpdesk and so on) to AI tools needs 105 unique point-to-point integrations built by hand. The same 15 systems each exposing one MCP server needs 15 connections, an 86% cut in the number of integrations to build and maintain.

How does MCP's architecture work under the hood?

MCP borrows its shape from the Language Server Protocol that standardised how code editors talk to language tools. Three parts make up every MCP setup, and each one has a clearly separated job, which keeps the protocol simple enough to extend without breaking existing integrations.

The host

The host is the AI application itself: a chatbot, an IDE assistant or an internal agent platform. It holds the conversation with the user and decides when a task needs outside data or an outside action, then asks an MCP client to fetch it.

The client

The client lives inside the host and speaks MCP to exactly one server at a time. It handles the JSON-RPC 2.0 messages back and forth and keeps each server's session separate from the others.

Two ways exist to move those messages. A local server on the same machine as the host talks over standard input and output, the way most developers first try MCP on a laptop. An enterprise server usually sits behind the network instead, reachable by many hosts over HTTP, the transport the July 2026 update reworked to be stateless.

The server

The server is the thin wrapper a system owner builds once, exposing that system's data or actions (a customer record, a stock check, a ticket update) through the same MCP interface. A large enterprise might run dozens of these, one per business system, built once and reused by every AI tool that needs it.

Underneath host, client and server sits a second layer: what a server can actually offer. MCP defines three primitives, tools an AI model can call to take an action, resources it can read for context, and prompts a system owner can package as ready-made instructions.

A CRM server might expose a "create contact" tool, a "customer record" resource and a "draft follow-up" prompt, all through one connection. A new AI tool inherits all three the moment it connects, rather than needing each built separately.

The protocol itself keeps changing. The 28 July 2026 specification update moved MCP from a stateful, session-based connection to a stateless request and response model for HTTP transport, and tightened authentication with OAuth 2.1 and RFC 9207 issuer checks, both aimed squarely at enterprise deployments rather than a single developer's laptop.

How does MCP compare with point-to-point APIs and iPaaS?

Enterprises already had two ways to wire systems together before MCP arrived. The table below sets all three side by side, using the same 15-system example from above so the integration count lines up.

The connection count looks similar between iPaaS and MCP because both are hub-based rather than point-to-point. The difference is who is on the other end: iPaaS mostly moves data on a schedule, while MCP is built for an AI model asking a live question and taking a live action in the same exchange.

Maintenance load splits the same way. When an upstream CRM changes its API, point-to-point integration means finding and fixing every hand-built connector that touches it. Under MCP, that same change is a fix to one server, not to every tool that happens to call it, which is the whole of the M plus N argument showing up again at update time rather than at build time.

How fast is enterprise MCP adoption running in 2026?

MCP's own maintainers reported close to half a billion downloads a month across its main software development kits by July 2026, with the TypeScript and Python versions each passing one billion downloads in total since Anthropic released the protocol as an open standard in November 2024.

UK adoption is climbing from a much smaller base. Only 29% of UK businesses reported using at least one AI technology in June 2026, an increase of eight percentage points on the year, rising to 49% among businesses with 250 or more staff, up 13 percentage points on the year.

The bigger UK theme is not AI adoption itself but what comes after it. techUK's own account of the year put it plainly: 2023 and 2024 were about generative AI hype, and 2025 became the year integration had to catch up, since agentic AI risks becoming what techUK calls a "side project" without real connection into existing enterprise systems, a theme it expects to carry into 2026.

The same source points to a practical shift already under way alongside MCP: low-code and no-code integration tooling is pulling more of this work away from specialist developers and into the hands of business users who know the systems best, which lowers the bar for who inside a UK enterprise can actually stand up a new MCP server.

What security and governance risks come with adopting MCP?

Every new MCP server is a new door into a business system, so the question for enterprise IT is not whether to build a server but who is allowed to call it, with what permissions, and for how long. The July 2026 specification's move to OAuth 2.1 and RFC 9207 issuer checks was written to answer exactly that.

UK financial services already sits closest to this pressure. More than 80% of financial services firms are already using or adopting AI, Financial Conduct Authority chief executive Nikhil Rathi said in a speech on 24 June 2026, with human oversight and audit trails named as live, unresolved questions rather than settled ones.

Legacy systems make this harder in practice, not just in theory. The Bank of England's own IT spend has been driven up by manual processes and older systems, and integrating the Prudential Regulation Authority's applications duplicated work that is still being unwound.

There is a second risk that has nothing to do with legacy systems: provenance. Anyone can publish an MCP server, and an AI agent instructed to call one that has never been checked can be tricked into leaking data or taking an action nobody asked for, the same prompt injection problem security researchers have raised since MCP's earliest months. (Treat an unreviewed third-party server the way you would treat unreviewed third-party code, because that is exactly what it is.)

None of that is a reason to avoid MCP. It is a reason to treat every MCP server exactly like the API it is: reviewed, permissioned, logged, and owned by someone who can be asked what it does when an auditor turns up.

What should a UK enterprise IT team do before rolling out MCP?

None of the steps below are exotic. They are the same discipline any new class of integration earns before it touches production data, adapted for what is genuinely new about MCP.

  • Inventory the systems you would actually connect. List the ones an AI tool would realistically need live access to this year, not a wish list of everything in the company.
  • Pick the auth model before the first server ships. OAuth 2.1 with issuer validation is the direction MCP itself has taken; match it rather than bolting on something weaker later.
  • Name an owner for every MCP server. The Bank of England's experience shows what duplicated, unowned integrations cost to unwind years later.
  • Log every call an AI client makes through a server. The FCA's open questions on audit trails and human oversight are exactly what a logging layer needs to answer.
  • Start with one system, not fifteen. The M plus N maths only pays off once several systems and tools are involved; a single pilot server proves the pattern without betting the whole integration estate on it.

One more UK-specific factor is worth naming plainly. Government's own roadmap for modern digital government, published January 2026, calls for public services to adopt a standard set of APIs and events for new services. A supplier building an MCP server for a public sector client should expect that standard, not a bespoke one, to be the one it gets measured against.
